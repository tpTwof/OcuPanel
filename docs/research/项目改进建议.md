# OcuPanel 项目改进建议

> 2026-11-19 审阅快照。后续修复及验证结果见[当日 v2](../../update/26-11-19-v2.md)。

建议下一阶段集中做两件事：补齐报告图片的账号归属检查，建立一套能分别评价青光眼影像、检索和报告质量的独立样例。前者影响多人使用时的数据隔离，后者决定后续投入应落在模型、资料还是生成流程。以下为基于 2026-11-19 工作区的静态审阅，优先级是建议，未估算工期。

## 当前需要改进的模块

| 优先级与模块 | 当前依据及影响 | 建议与验收方式 |
| --- | --- | --- |
| 优先处理 · 报告图片归属 | PDF 导出按用户和报告 ID 读取记录；图片读取虽然要求登录，但只检查文件名和文件是否存在，缺少账号与报告的关联检查。[报告服务](../../backend/report/service.py) | 让图片随所属报告授权。用两个测试账号覆盖本人查看、他人访问和文件缺失三种结果，同时验证本人历史报告仍能显示叠加图。 |
| 优先处理 · 输入可判读性与青光眼验证 | 当前可拦截过小或纯色图。已记录的真实模型推理使用带 AI 生成标记的示例，无法据此估计模糊、曝光异常或不同设备下的表现。[视觉验证记录](../../backend/vision/README.md) | 先约定图像质量标签和参考标注，按患者隔离评估样本。分别报告不可判读图的放行率、可判读图的误拒率、分类漏检与误报、视杯和视盘分割 Dice、面积等效杯盘比误差。注明每项分母，缺少对应标注的指标保留为待测。 |
| 优先处理 · 证据与报告评估 | 检索、Director 和引用核验都已接通。编号正确仍可能引错条款，引用核验也无法发现所有与原始病例不符的测量或描述。[检索服务](../../backend/knowledge/service.py) · [核验器](../../backend/agents/verifier.py) | 固定一批有参考条款的问题，另设语料无法回答的题目。人工逐句标记病例事实一致性、条款支持性及拒答合理性，分别统计检索未命中、生成误引和核验误放行。保存评审分歧及复核结论。 |
| 随后处理 · 报告保存与重复提交 | 正文流程依次保存叠加图、报告和两条会话消息。中途失败可能留下部分结果；同一请求重试会再次运行模型。[报告服务](../../backend/report/service.py) · [存储](../../backend/utils/storage.py) | 为一次提交建立可复用的请求标识，报告和会话消息在同一数据库事务中写入，并为文件保存失败提供清理。以模拟写入中断和网络重试验收，同一提交最终只出现一份完整结果，用户主动重新分析仍可生成新报告。 |
| 随后处理 · 多病种归档与导出 | 视觉层按病种保存结构化输出，报告交付层仍单列杯盘比和单张叠加图。视网膜分数可显示在文字中，历史数据难以逐项比较。历史 PDF 已能复用保存的正文和证据。[视觉模型](../../backend/vision/models.py) · [报告服务](../../backend/report/service.py) | 归档每个病种的指标名称、值、含义、模型来源、警告及核验状态。分别用仅青光眼、仅 DR、联合分析和旧报告核对页面与 PDF；未评估字段应明确标注，关闭核验的结果在导出后仍可辨认。 |
| 随后处理 · 长会话与病例切换 | 眼科上下文固定最近报告，会话详情读取完整消息。一个会话分析多次时，用户追问早先报告可能引用错对象；模型输入已有预算，历史读取仍随会话增长。[上下文选择](../../backend/chat/context.py) · [会话存储](../../backend/utils/storage.py) | 在追问入口显示关联报告并允许选择，历史消息按需分页。用同一会话中两份结果不同的报告验收，确认追问和引用对应所选病例，再测长会话首次加载时间。 |

## 对已有规划的取舍

[历史 SPEC](../SPEC-Ophthalmology-Copilot.md) 给出了多模型、图谱和多智能体的扩展设想；[阶段性汇报](../阶段性汇报.md) 则把独立验证排在下一阶段。建议沿用后者的顺序，并作以下调整。

| 规划事项 | 判断及原因 | 建议的决策条件 |
| --- | --- | --- |
| 按历史 SPEC 的“当前实现对照”排期 | 该表仍写图检索占位、只支持青光眼、历史 PDF 待做。如今已有图检索融合、可选 FLAIR 和历史导出，直接沿用会造成重复开发。[图检索](../../backend/graphrag/README.md) · [报告接口](../../backend/report/api.py) | 保留历史记录的日期，将后续排期绑定到可演示入口及缺口。例如把“实现历史 PDF”改为“验证历史导出中指标与核验状态的完整性”。 |
| 数周内接入多个 VLM，再做三路集成 | 同时更换模型、组合方式和报告生成输入，会使效果变化难以归因。DR、AMD 当前只有未经校准的匹配分数，尚无分级标注或项目内验证结果支撑扩展承诺。[视网膜模型说明](../../backend/vision/README.md) | 每轮只研究一种病种、一个目标和一个候选模型。锁定数据划分与基线，记录新增正确发现、误报、耗时和资源占用，再决定保留、集成或停止。 |
| 先换图谱框架，再扩充语料 | 已有本地图谱、带出处的条款和基础检索回退。更换框架本身无法补齐资料覆盖，图路径也不能单独证明答案成立。[知识检索](../../backend/knowledge/README.md) · [图谱实现](../../backend/graphrag/README.md) | 固定语料和问题，对比基础混合检索与叠加图检索，单列跨概念问题。按错误定位行动：资料缺失补条款，图中关系错误修数据，现有实现确实受规模或功能限制时再评估迁移。 |
| 将动态会诊、消息总线列为默认升级 | 当前已按病种选角色，并行出稿后由 Director 综合。角色增多会增加调用与等待，项目尚缺少角色间协商能解决哪些错误的对照结果。[专科流程](../../backend/agents/README.md) | 固定病例、证据和模型，对比单角色与现有多角色流程，记录事实错误、相互矛盾的建议、调用次数和耗时。若特定分歧持续出现，再对该场景试验一次定向复核。 |
| 把“启用检索和核验”作为一项实验 | 阶段性汇报的对照能衡量组合收益，但难以判断是检索改善了草稿，还是核验拒绝了更多回答。只看最终交付文本还会遗漏拒答代价。 | 离线分三组评估：基础生成、加入检索、加入检索并核验。保持病例和模型配置一致，保留各阶段样本；同时报告有据回答比例、错误放行和不必要拒答。 |

## 建议的交付顺序

1. **多人演示前**，完成图片归属检查，用两个账号验证结果隔离。
2. **下一次课题验收前**，交付青光眼病例清单、标注口径、分阶段评估表及首轮错误分析。可先小规模试评，保留独立样本供后续对照。
3. **下一轮功能投入前**，依据错误分布挑一项改动，在相同样本上复测。若主要问题是输入不可判读，就先解决图像质量；若资料已命中但引用仍错，就先改生成或核验。多病种扩展和框架迁移各自单独决策。
