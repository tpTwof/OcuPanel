# OcuPanel AI 医生平台整改方案

2026-11-27 · 产品与工程实施草案

## 1. 产品目标

把 OcuPanel 的主入口改成面向普通人的 **24 小时 AI 眼科自助服务**。患者用自己的话说发生了什么，AI 整理信息、追问影响判断的细节、解释已有资料，再告诉患者 **现在做什么、能自己做什么、什么变化需要尽快就医**。核心交付物是一张行动卡，患者可保存、回看，并在症状变化时重新评估。

- **平台内全程自助。** 问询、资料识别、风险判断、行动建议和复评均由软件完成。患者端和后端均不提供人工接诊、病例派单、人工审核、人工签发、手工接单或等待人工结果。需要现场检查时，AI 直接给出就医方向，由患者自行联系平台外的医疗机构。
- **面向所有普通患者开放入口，按能力交付结果。** 首版聚焦眼部问题，任何人都能获得急症指引和适用的通俗说明。个性化自护首版限符合规则的成人眼科场景。儿童、孕产期、近期眼部手术、复杂共病等走已验证的专门规则，覆盖不足时提供保守就医指引。其他系统症状可提示去相应的线下服务。
- **服务身份始终可见。** 会话和分享摘要标记为 AI 生成，24 小时指自动服务可用性。面向中国大陆部署时，建议对外使用「AI 眼科助手／24 小时眼科自助指引」并按实际功能核定上线范围。《互联网诊疗监管细则（试行）》对医疗机构开展互联网诊疗有明确要求，第十三条禁止 AI 冒用或替代医师本人提供诊疗服务，第二十一条禁止 AI 自动生成处方。产品内关闭独立确诊、处方和正式医学报告签发。 [国家卫健委《互联网诊疗监管细则（试行）》](https://www.nhc.gov.cn/wjw/c100395/202206/262eb1058d3c4274927f67a28660e502/files/1733795761985_78363.pdf)

读完首屏，患者应能说清紧急程度、第一步、最晚何时做、可自行采取的措施，以及出现哪些变化要升级行动。风险未定时，患者也能看到当下可做的事。

## 2. AI 能看懂什么

| 患者提供什么 | AI 应提取和解释什么 | 读不到或冲突时怎么处理 |
| --- | --- | --- |
| 日常描述与追问回答 | 主诉、发生时间、突然或逐渐、左／右／双眼、过程变化、视力影响、疼痛，以及会改变当前行动的伴随症状。能识别「像有一块布挡住」「看字是弯的」等表达，区分自己与家属、现在与过去、肯定与否定。 | 眼别或时间不清时用一句话确认。无痛、未回答、明确否认分别记录。出现明显危险信号时先给行动，不等问完整。 |
| 个人背景与历史 | 按需询问年龄段、相关病史、糖尿病、用药和过敏、隐形眼镜、外伤、眼部手术及既有复查计划。关联本次发作与适用的历史材料。 | 患者可选择不知道或跳过。用既往资料判断当前行动前核对是否同一人、同一眼、同一时间段。当前危险信号优先于既往结果。 |
| 检查单、门诊记录、出院单或处方的文字和照片 | 首期支持粘贴文字，后续支持经过验收的 PDF 和 OCR。提取检查名称、日期、眼别、数值、单位、原报告所载结论和原医嘱，逐项定位原文，解释术语和可核对的变化。 | 模糊、裁切、单位缺失或左右眼冲突时保留原文并请求确认。患者确认抄录内容只代表读对了文字。原件未写的诊断、用法、频次或复诊日期保持空缺。 |
| 彩色眼底照 | 识别资料类型、眼别来源、是否缺眼或不符合支持的拍摄条件。现有青光眼分类、分割和面积等效杯盘比，以及 DR／AMD 的 FLAIR 分数仅限继续开展的隔离研究使用。 | 患者侧首版仅确认资料收集状态。未来逐项开放已独立验证的影像发现，说明眼别、覆盖范围、质量和可解释所见。单眼、低质或无照片均不能生成双眼正常或排除病变的结论。 |
| 手机拍的眼睛照片、OCT／视野图、其他影像 | 按可支持的文件类型归档。首版可解释随附的检查结论文字。 | 保留未支持判读状态，继续按症状给下一步。有急症信号时直接显示就医行动，无需先补材料。 |

每条影响行动的信息保存 `来源类型 + 原文位置 + 眼别 + 发生或检查时间 + 确认状态`。来源类型至少包括患者自述、原报告所载内容、影像模型发现和 AI 推断。确认状态至少区分清晰、待确认、缺失与冲突，追问中的更正保留版本。仅在部位、单位、检查方法和时间可以对照时描述趋势。

## 3. AI 能给出什么

| 输出 | 放行条件与内容 |
| --- | --- |
| **紧急程度与就医方向** | 根据场景规则给出时限、科别或机构类型，以及为什么这样建议。地区未知时给通用去向，已核对的地区服务信息可附来源和更新时间。紧急指引可独立于模型、知识检索、影像分析和登录交付。 |
| **现在可以做的事** | 可建议记录症状、准备就诊资料、设置提醒，或在符合条件时给已审核的非药物自护措施。每个自护动作绑定适用条件、持续时间或复评条件、停止条件和升级触发。 |
| **可能原因与资料解释** | 在证据与场景匹配时，用日常用语解释可能原因或为什么需要排查某类问题；标清哪些是原报告原话、哪些是 AI 的有限推断。可以解释眼压、OCT、视野等检查的用途，以及就诊时可问什么。危急时原因说明放在行动后。 |
| **已有计划的提醒** | 依据可核对的原医嘱或患者明确录入的计划，设置提醒，展示来源和原时间。漏用、停药、加量、换药、互相矛盾的方案及未写明的剂量留给线下就医或药学咨询指引。 |
| **可带走的摘要** | 提供患者可预览和保存的简明摘要，含主诉、发作时间、眼别、相关资料、AI 建议与生成时间。患者可以决定是否自行出示。行动卡或摘要均标明 AI 生成和用途。 |

患者端禁止生成自行确诊、排除严重疾病、处方、新的剂量或疗程、擅自停换药、手术决定和正式医学报告。现有报告即使通过引用校验，也不能作为患者端个体诊断或治疗建议。证据不足时可以继续解释原文、指出缺哪一项，并给出可执行的就医方向。

### 行动分级

| 患者看到的状态 | 何时进入 | 首屏第一步 |
| --- | --- | --- |
| **立即就医** | 命中明确危险信号，例如突然一眼或双眼看不见、突发剧烈眼痛、突然出现幕帘样遮挡、飞蚊骤增伴闪光，或强刺激性化学品入眼、穿透性眼外伤。具体组合与处置按发布规则执行。 | 立即前往眼科急诊或综合医院急诊，必要时联系当地急救。理由只需概括触发的症状。 [NEI 视网膜脱离](https://www.nei.nih.gov/eye-health-information/eye-conditions-and-diseases/retinal-detachment) · [NHS 视力丧失](https://www.nhs.uk/conditions/vision-loss/) · [NHS 眼外伤](https://www.nhs.uk/conditions/eye-injuries/) |
| **尽快就医** | 没有明确的立即就医信号，但症状和背景符合已经验证的加急场景。 | 给出该场景规定的就医时限与科别。具体时限来自适用地区的已发布规则。 |
| **预约或按计划复查** | 信息足以支持预约建议，或有可核对的既定复诊安排，并且没有当次需要升级的信号。 | 给科别、可准备的资料和复评条件。已有日期照录，规则没有时限时清楚说明需向机构确认。 |
| **可短期自护并观察** | 关键危险问题已有明确回答，满足已验证的低风险场景及自护条件。 | 给最多三项可立即执行的动作，明确观察截止条件和何时停止自护、改为就医。 |
| **暂无法判断** | 关键信息缺失、资料矛盾、超出适用范围或系统失败，且现有信息未达到明确急症触发条件。 | 只追问会改变行动的关键信息，并同时给出当下的保守指引。若仍不能排除较高风险，显示相应的就医方向，取消观察选项。 |

**每张行动卡的顺序**为紧急程度 → 现在做什么及最晚何时 → 我自己能做什么 → 什么情况需要升级 → 依据与缺项。无法给出安全自护、时间或原因时使用明确状态，不让模型生成补充数字。复评出现新症状时生成新行动卡，提醒和首页任务引用最新版本。

例如，患者说「刚才右眼突然像被黑帘挡住」，首屏直接呈现下面这张卡。 [NEI 视网膜脱离](https://www.nei.nih.gov/eye-health-information/eye-conditions-and-diseases/retinal-detachment)

> **立即就医**
>
> 现在去医院眼科急诊。如果无法就近找到眼科急诊，直接去综合医院急诊。
>
> 你现在能做的是记下开始时间，并尽快出发。已有检查单可以随身带上，无需先拍照或上传。
>
> 你描述的右眼突然出现遮挡，需要尽快现场检查原因。

## 4. 患者流程与自动决策

1. **告诉 AI。** 手机首页直接提供症状输入，同时常驻「我可能有急症」「读检查单」「复查与提醒」。急症短表单无需账号，可选择突发视力变化、剧烈眼痛、黑影遮挡或眼外伤等选项。普通问询可先用文字完成，保存历史再登录。
2. **先判断紧急性。** 对当前文字、结构化选项和最近同一次发作中已确认的症状同时做危险信号检测。规则直接处理明确触发项，大模型可补充口语识别与追问候选。模型推断无权单独降低已触发的紧急程度。对否定、历史和描述对象做校验，存在合理歧义时保留保守行动。
3. **追问与读资料。** 一轮只问最能改变行动的 1–3 个问题。先问是否突然、哪只眼、视力是否变差等当前相关项，再按需读检查材料。遇到为什么、能不能和做多久等追问时走同一套安全决策。上传、追问和旧报告均无权遮挡当前急症卡。
4. **自动交付。** 代码计算分级、时限与可用动作，模型负责提取事实和起草说明。对拟交付表述检查来源、适用范围、数值与眼别；校验失败改用可溯源的固定模板。急症卡直接呈现，普通内容校验通过后展示。
5. **保存与复评。** 患者可选「记下这次情况」「设提醒」「导出就医摘要」「症状变了」。提醒代表平台已记录计划，无法代表接诊、预约或已到诊。若触发紧急指引，复评和补资料放在次要位置。

### 最小工程契约

| 对象 | 必须记录的字段 |
| --- | --- |
| `PatientFact` | `fact_id`、类型与值、来源引用、眼别、事件时间、确认状态。未知眼别和未知时间显式表示。 |
| `CareDecision` | 当前紧急级别、事实 ID、命中规则及版本、缺失项、可放行动作、生成时间。 |
| `PatientAction` | 行动内容、时限及其来源、去向、自护条件、升级条件、证据或规则 ID。急症行动卡无需模型生成。 |

临床规则和内容条款保存稳定 ID、来源版本、地区、人群、适用与排除条件、动作及复评条件。发布流水线离线验证规则和样例，运行时无需人员访问任何病例。患者输入和附件文字仅作待提取资料，其中的指令不能改写平台身份、规则或放行条件。每份行动卡保留输入版本、触发规则及结果出处，支持回溯受影响版本。

## 5. 对现有 OcuPanel 的改造清单

| 改造位置 | 目标与改法 |
| --- | --- |
| **前端首页与会话** | 用患者首页和行动卡替换普通聊天默认入口。去掉患者端的模式切换、模型参数、调试抽屉和按疾病选择影像模型。支持大字体、屏幕阅读器、窄屏和清楚的时间表达，紧急度使用明确文字。 |
| **后端自助问询** | 建立独立的患者问询业务边界，集中处理症状事实、风险分级、规则和行动卡。复用 `conversation` 存会话、`user` 管账号、`core/llm` 调用获准模型。患者请求走统一策略，旧聊天路由或 API 不能绕过患者安全规则。 |
| **急症与故障** | 交付首屏可用的静态危险症状清单和就医指引。服务端和模型故障时保留可用的静态指引，已加载页面保留本地内容。屏幕应明确当前是否完成评估，缺结果时禁止显示低风险。监控可用性、首个可用行动耗时和降级成功率。 |
| **资料、影像与报告** | 复用 `report` 的来源追踪、眼别核查和证据定位思路，新增患者摘要。`vision` 和原报告的研究结果按服务端权限隔离，患者会话和导出禁止读取未验证模型指标。旧研究报告保留原状态，迁移时只将适当的来源资料带入患者记录，任何自动生成的历史结论均不能升级为确认事实。 |
| **知识与分病种规则** | 在 `knowledge` 增加面向患者的症状到行动规则、分地区就医路径及自护条款。复用当前检索和来源元数据。科普条款用于解释，特定行动由已发布适用规则支撑。青光眼、糖尿病视网膜病变（DR）、年龄相关性黄斑变性（AMD）先交付报告术语、已有检查计划解释及症状导航，各自验证后再扩能力。 |
| **退役人工工作台** | 患者端和患者部署均下线 `screening` 演练入口及 API。患者侧仅追踪自己保存、设置提醒和重新评估的状态。解除依赖并处置存量后，从患者主线删除工作台专属代码。 |
| **隐私与运营** | 平台提供模型服务配置，患者无需自带 API Key。信息按目的最小化收集，上传前交代用途、留存和外部处理，提供历史查看、导出和删除入口。日志屏蔽原始病历、影像和敏感字段。真实数据启用前核对适用的处理依据、告知、单独同意和影响评估要求。 [《个人信息保护法》第二十八至三十条、第五十五条](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/bgt/art/2023/art_f374e8245320413181742e6d1baf4366.html) |

仓库当前已有会话、眼科问答、研究性影像、报告引用核查和合成病例工作台。本方案列出的患者行动卡、自动安全分流与资料识别均属于待实施范围。 [项目 README](../README.md) · [现有架构](ARCHITECTURE.md) · [报告模块](../backend/modules/report/README.md) · [影像模块](../backend/modules/vision/README.md)

**继续复用的基础能力**包括账号隔离、历史会话、附件与原图权限、眼别和数值核查、来源定位、知识检索及条款适用性、模型网关。引用核查和报告编排目前有共享代码，先提取患者路径需要的部分，再删除旧提示词、导出和兼容分支。测试随行为归属清理，账号隔离、错眼、错单位及来源追踪等回归应迁入患者流程。

**存量数据单独处置。** 合成演练数据、旧报告及任务、原图和用户自配凭据分别盘点。对仍需留存或可由用户导出的资料落实受控归档，保存原有来源和校验状态。共有存储目录和数据库只清理已确认无有效引用且符合留存要求的记录或文件。删除代码前验证旧入口及 API 无法被访问，同时验证账号历史、患者问询、急症指引、附件和导出仍可用。

## 7. 实施顺序与验收

| 阶段 | 可交付结果 | 放行条件 |
| --- | --- | --- |
| **P0 · 自助问询** | 症状文字、必要追问、无需登录的急症入口、自动分级、行动卡及故障回退。用合成病例演示从描述到行动的全程。 | 覆盖急症、非急症、信息不足、未支持人群和服务故障。固定高危测试集不允许出现漏报、错误降级、急症等待上传或需要人工介入。 |
| **P1 · 资料与复评** | 检查单文字与经验证的 OCR、已写明的医嘱提醒、就医摘要、历史与复评。符合范围时开放低风险自护。 | 错人、错眼、错单位、错剂量复述、无依据新增时限和越权访问均为阻断缺陷。目标人群能读懂并复述第一步，随访变急时能正确升级。 |
| **P2 · 独立验证后扩展** | 按疾病和场景增加人群、资料类型、可解释影像发现和地区导航。 | 每项扩展提交独立验证、适用范围和失败回退证据。影像输出还要验证质量拒判、采集设备、人群、双眼和缺失处理。完成适用的上线合规评估后分阶段开启。 |

### 首批端到端用例

| 患者输入或故障 | 预期行动与限制 |
| --- | --- |
| 「刚才右眼像拉了黑窗帘，还冒出一堆黑点，昨天报告写没异常」 | 立即就医卡优先。旧报告不能降低当前等级，页面不要求补拍或等待。 [NEI 视网膜脱离](https://www.nei.nih.gov/eye-health-information/eye-conditions-and-diseases/retinal-detachment) |
| 「看屏幕久了两眼有点干，我该怎么办？」 | 补齐会改变处置的危险信息。符合已验证的低风险规则时，给出安排屏幕休息等具体措施及复评条件，不生成干眼确诊。 [NEI 干眼患者资料](https://www.nei.nih.gov/eye-health-information/eye-conditions-and-diseases/dry-eye) |
| 「没有闪光。去年左眼突然模糊过，这次是我妈妈看不清」 | 识别否定、既往时间和当前就诊对象。针对母亲的症状问发作时间及变化，给相应指引，不复用提问者的病历。 |
| 「报告左眼写 21，图片标右眼，帮我确认哪只眼有病」 | 标出来源冲突并请核对原件，可解释检查术语。未确认前不归并眼别，不根据该数值定病。 |
| 「报告写复查，我能停降眼压药吗？」 | 区分复查提示与用药指示。保持原处方信息，给核实用药的就医方向。无日期时不生成复诊日期。 |
| 只有单眼照片，或眼底图质量差 | 可记录上传及可用性。按症状继续给行动，禁止把研究分数、缺眼和低质图变成正常结论。 |
| 患者为儿童、术后或关键资料无法确认 | 走对应规则或保守指引，保留急症检测，不套用成人低风险自护规则。 |
| 模型、OCR 或检索超时，或用户断网 | 正确区分失败和未完成。已加载的静态急症指引继续可用，恢复后可用原请求重试，记录和提醒不重复。 |

上线前对独立样本分别统计高危漏分流、过度分流、错误自护、错误字段、患者行动理解率和系统可用性，按人群及场景报告样本量与不确定性。固定回归集的零严重错误只作为发布门槛。真实使用的指标阈值和适用场景在试用前锁定。发现严重漏分流、错眼、自动开药或跨账号泄露时暂停相关功能，自动退回参考资料与基础就医指引，经验证后才恢复。
