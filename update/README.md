## 记录规则

1. **按业务可对照的状态记录。** 一条记录可以涵盖多个提交，也可以记录已经实现但尚未提交的工作区状态。以功能实际完成或存档的日期为准，标明记录的是上游、工作区、已发布版本还是计划。仅调整代码结构且业务行为相同的改动，可归入相关模块的一句说明。
2. **文件使用 `YY-MM-DD.md`。** 例如 `26-11-18.md`。`Medchat.md` 是保留的上游基线。
3. **同一天有多轮业务更新时，在日期后加版本号。** 第二轮出现时，将当天原文件重命名为 `YY-MM-DD-v1.md`，新增 `YY-MM-DD-v2.md`，并同步更新索引和引用链接。此后依次递增，每轮对照紧邻的上一版本。修正错字或补充验证结果可更新原记录。
4. **第一节固定写「更改了哪些」。** 先概括新增、调整、移除的业务能力，以及对用户或下游环节的影响。初始基线用同一标题列出初始能力。
5. **按业务模块逐项写前后差异。** 对受影响的模块写清入口与输入、触发条件、处理职责、输出和用户可见变化。覆盖重要条件分支、失败或拒答、是否保存、历史数据如何打开或导出。只写与理解行为有关的实现名，提交和代码链接可以放在末尾作为出处。
6. **给出端到端流程和验证边界。** 写清常见路径以及会改变结果的分支，有多条分支时可用流程图。注明验证过哪些场景、哪些结论仍需验证。计划中的能力单独标为待验证或后续事项。
